# Phoenix Threat Model

This document describes the deployment envelope Phoenix is designed for, the core threats it mitigates, the trust boundaries, and what remains out of scope.

## Deployment envelope: LAN-scoped by design

Phoenix is built for a single machine or a local network — a workstation, a
homelab, a small team's LAN. That is the product envelope, not a suggestion:

- **In scope**: loopback deployments (the default) and LAN deployments where
  the operator controls the hosts that matter.
- **Out of scope and unsupported**: internet/WAN exposure, public ingress,
  and operation on networks assumed hostile. Do not port-forward Phoenix,
  put it behind public ingress, or run it on infrastructure you do not
  control. Every mitigation claim in this document assumes the envelope;
  none of them are load-bearing against internet-scale attackers.

**LAN is in scope, but the LAN is not a trust boundary.** A typical LAN
carries containers on shared bridges, IoT devices, guest WiFi, and anything
an attacker gained by compromising one host. Phoenix is a credential
concentrator: sniffing a single bearer token yields everything that token's
ACL permits, not one secret. Treat every wire crossing as hostile even
inside the envelope.

### Transport rules that follow from the envelope

1. **Plaintext HTTP on loopback is the safe, supported default.** Loopback
   traffic never reaches a NIC; TLS adds nothing there, and the dominant
   deployment is single-machine.
2. **The moment traffic crosses a wire, enable TLS.** Binding a non-loopback
   address (`0.0.0.0`, a LAN IP) without TLS puts bearer tokens and secret
   values on the network in cleartext. The server detects this at startup
   and emits a loud warning naming exactly what is exposed — it warns, it
   never refuses to start. The CLI, SDK, and MCP transport apply the same
   posture to plaintext non-loopback URLs.
3. **TLS does not require mTLS.** The `tls:` config block enables HTTPS on
   its own, using the certificate generated by `--init`. mTLS remains an
   optional client-certificate layer on top. See
   [LAN Deployment](lan-deployment.md).

## Scope and assumptions

- Phoenix protects secret access for AI-agent-driven workflows.
- Agents and tools are treated as potentially untrusted consumers.
- The Phoenix host, config, and key material are assumed to be administratively controlled.
- LAN-resident network attackers (sniffing, spoofing, a compromised
  neighbor host), prompt-injection side effects, and credential leakage
  are in scope. Internet-scale network attackers are not — see the
  deployment envelope above.

## Security goals

1. Keep secrets encrypted at rest.
2. Ensure only authorized agents can read/write/delete allowed paths.
3. Require strong caller identity and optional attestation before revealing secret values.
4. Preserve an audit trail for every access decision.
5. Limit blast radius when credentials leak.

## Assets

- Secret values
- Master key / wrapped DEKs
- Agent credentials (bearer tokens, mTLS certs, short-lived tokens, session tokens)
- ACL and attestation policy config
- Audit log integrity
- Dashboard session cookies (when dashboard is enabled)

## Trust boundaries

1. **Client/agent process** → **Phoenix API**
   Authentication, ACL checks, and attestation are enforced here.
2. **Phoenix API** → **Secret backend**
   File backend or external backend reads are mediated by Phoenix policy.
3. **Phoenix runtime** → **Storage and key files**
   File permissions and host hardening matter for confidentiality.
4. **Browser** → **Dashboard** (when enabled)
   Cookie-based auth with separate credential. See "Dashboard attack surface" below.

## Threats Phoenix addresses

- **Prompt-injection-induced secret exfiltration**
  Reference-first workflows (`phoenix://` + policy-gated resolution) reduce plaintext exposure in config/prompt paths.
- **Unauthorized cross-agent access**
  Per-agent ACL path rules enforce least privilege.
- **On-wire credential and secret interception**
  TLS (the `tls:` config block, or mTLS) encrypts every request that crosses
  a wire. The safe default is loopback, where no wire is crossed; the server
  warns loudly at startup when a non-loopback bind would put bearer tokens
  and secret values on the network in cleartext.
- **Credential replay / misuse**
  mTLS, IP binding, cert pinning, nonce challenge, and short-lived tokens reduce replay value. Session tokens are scoped, time-limited, and individually revocable.
  Note: IP binding and `source_ip` policy are meaningful only inside the LAN
  envelope, where addresses are operator-assigned and not attacker-chosen.
  They are not a defense against internet-scale attackers (out of scope).
- **Operational leakage**
  Structured audit logs record allows/denies without writing secret values.
- **At-rest theft of store data**
  AES-256-GCM envelope encryption protects persisted values.
- **Rotation failure corruption**
  Two-phase key rotation + backup path supports recovery.

## Session identity threats

Session tokens (`phxs_` prefix) introduce additional attack surface:

- **Token theft**: Session tokens are bearer-like. If leaked, an attacker gains the
  role's scope until expiry or revocation. Mitigated by short TTLs (default 1h),
  per-session revocation, and binding to the minting agent's identity.
- **Privilege escalation via role config change**: Roles are re-checked at renewal
  time. A role config change that widens scope does not retroactively expand active
  sessions — the session keeps the scope it was minted with.
- **Step-up bypass**: Step-up approval is enforced server-side at mint time. An agent
  cannot mint a step-up role without human approval. The approval re-checks role
  config, `allowed_agents`, bootstrap trust, attestation, and seal key requirements
  at approve time to prevent stale-config attacks.
- **Wrong agent asks for a powerful role**: `bootstrap_trust` checks *how* a caller
  logged in, not *who* it is. `allowed_agents` on a role binds it to named agents;
  it is checked at mint, at approval (API and dashboard) and at renewal
  (`403 ROLE_NOT_ALLOWED`). A role without it is unbound: the server warns at
  startup and the dashboard card shows a badge, but nothing is enforced. **The
  warning alone does not close the gap.** The next release makes `allowed_agents`
  required for `elevates_acl` roles.
- **Session token on admin endpoints**: Session tokens are explicitly rejected for
  admin operations (agent management, cert issuance, approval, revocation by other
  agents). This prevents a scoped session from escalating to admin access even if
  the underlying agent has admin ACL.

## Dashboard attack surface

When `dashboard.enabled` is `true`, the server exposes a browser-accessible admin
interface at `/dashboard/`. This is a materially different attack surface from the
API and must be evaluated separately.

### What the dashboard exposes

The dashboard can: view secret/agent/session counts, view and revoke active sessions,
approve and deny step-up requests (minting session tokens), approve and deny secret
access requests and revoke grants, view the full audit log, and view role
configuration.

The dashboard **cannot**: read or write secret values, create or modify agents, issue
or revoke certificates, or change server configuration.

Approval is the highest-risk action — it mints a session token for an agent.

### Authentication model

The dashboard uses a **separate auth surface** from the API:

- Single shared password (bcrypt hash in config) or PIN (constant-time compare)
- Cookie-based sessions with HMAC-SHA256 signed payloads and per-session nonce
- Single active session by default (configurable via `allow_multi_login`)
- Force Login as escape hatch for orphaned sessions (re-authenticates, invalidates prior)
- CSRF tokens embedded in the cookie and validated on every POST (including logout)
- Exponential backoff rate limiting per source IP (5 attempts, then 1s–60s delay)
- Full audit trail: login success/failure, force login, logout, expired/superseded
  cookie rejection, CSRF failures, and all mutations (approve, deny, revoke)

This is simpler than the API's auth model by design: the dashboard targets human
operators, not programmatic access. The trade-off is that all dashboard users share
one credential and are distinguished only by source IP in the audit trail
(`dashboard@<ip>`).

### Threats specific to the dashboard

| Threat | Mitigation | Residual risk |
|--------|-----------|---------------|
| Brute-force login | Rate limiting with exponential backoff, audit logging of failures | PIN mode has smaller keyspace; use password for non-loopback deployments. Per-IP rate limiting assumes LAN-envelope addresses; it is not sized for internet-scale credential stuffing (out of scope) |
| Session cookie theft (network) | `Secure` flag set when TLS detected; `HttpOnly` prevents JS access; `SameSite=Strict` prevents CSRF via cross-origin requests | Plain HTTP on a shared network exposes the cookie — **do not do this**. The server warns loudly at startup when the dashboard is enabled on a non-loopback bind without TLS |
| Session cookie theft (XSS) | `HttpOnly` flag; no user-supplied content rendered unescaped; embedded static assets (no CDN/external JS) | XSS in Go `html/template` is unlikely but not impossible if templates are modified |
| CSRF | Token-per-session in signed cookie, validated on all POST actions | Relies on `SameSite=Strict` + token check |
| Unauthorized approval | Same `ValidateForMint` safety checks as the API; role, `allowed_agents`, bootstrap, attestation, and seal key all re-verified | A compromised dashboard session can approve any pending request |
| Shared credential | All operators share one password/PIN; no per-user identity | Forensic distinction limited to source IP (`dashboard@<ip>`) |
| Config file credential exposure | Password stored as bcrypt hash in config (`password_hash`); plaintext rejected by validation; agent reading config gets only the hash | PIN mode stores plaintext PIN; use `password_hash` for non-loopback deployments |

### Deployment requirements

The dashboard **must** be deployed behind one of:

1. **Loopback only** — `server.listen: "127.0.0.1:..."`. Dashboard is unreachable
   from the network. Use SSH port forwarding for remote browser access. This is
   the default and the simplest safe option.

2. **Native TLS** — `"tls": {"enabled": true}`. TLS is native (using the
   `--init` server certificate), cookie gets `Secure` via `r.TLS != nil`.
   No client certificates required. Add `auth.mtls` on top if you also want
   client-certificate authentication for the API.

3. **TLS reverse proxy** — proxy terminates TLS, sets `X-Forwarded-Proto: https`,
   Phoenix detects this and sets `Secure` on the cookie. The server itself
   binds to loopback.

Exposing the dashboard over plain HTTP on a network you do not fully control is
**not acceptable**. The session cookie would transit in cleartext. The server
emits a prominent startup warning when the dashboard is enabled on a
non-loopback bind without TLS — it warns rather than refusing to start, and
the warning is the last thing logged before the server begins serving.

### When to disable the dashboard

Disable the dashboard (`"enabled": false`) when:

- You have no step-up approval roles (the primary use case for browser access)
- All operators have CLI/SSH access to the server
- You want to minimize the server's attack surface
- You are running in a high-security environment where a shared-credential
  browser surface is not acceptable

## Attestation controls (defense in depth)

Per-path policy can require combinations of:

- `require_mtls`
- `deny_bearer`
- `source_ip`
- `cert_fingerprint`
- `allowed_tools` / `deny_tools`
- `time_window`
- `process.uid` / `process.binary_hash`
- `require_nonce`
- `require_fresh_attestation`

## Request-use grants

An agent that is denied a secret can ask a human for temporary use of exact
paths (see [access-requests.md](access-requests.md)). A grant gives no new
token: the agent keeps its own identity. These are the threats and what
Phoenix does about them.

| Threat | Mitigation | Residual risk |
|--------|-----------|---------------|
| Request spam / approval fatigue | 3 pending per agent, 50 in total, 10 new requests per agent per hour, 10-minute cooldown after a deny, 10 active grants per agent. Limits survive a restart; each `429` has `Retry-After` | A human can still approve something without reading it |
| Social engineering via the reason | Reason shown as "Agent says (not verified)", escaped, control/bidi/zero-width characters stripped, 300-character cap, never a link. The approval card is built from server facts (paths, badges, attestation), not from the reason | The reason can still be a convincing lie |
| Approving more than intended | Exact paths only (no wildcards), at most 10, `read_value` only. The approver can untick paths and shorten the TTL, never widen. No bulk approve | |
| Self-approval / collusion | An agent can never approve its own request. API approval needs a name in `access_requests.approvers`; ACL `admin` alone is not enough | Two agents that are both approvers can approve each other's requests |
| Replay | Grants carry no token. Approve and deny are one-way saved transitions. Dashboard POSTs keep CSRF and `SameSite=Strict`. IDs are 128-bit random | |
| Stolen agent token | It can file requests (the human sees the source IP) and could use a live grant only from the bound IP, with the agent's registered seal key, as a non-session call. Sessions never use grants. Grants are short and revocable | A thief who also holds the agent's seal private key, on the bound IP, can use a live grant |
| Compromised agent | `require_sealed` sends granted values only sealed to the agent's own registered seal key | Sealed-only does **not** stop a compromised agent: it holds its own seal private key and can decrypt and leak the value. Sealing protects the value on the wire and in tool output, not from the agent itself |
| Unseal after the grant ends | Grant-only access never makes `allow_unseal` true, so an envelope cached while the grant was active cannot be unsealed by plugin unseal tools later | |
| Name reuse after agent delete | Delete revokes the agent's grants first, under one lock, and keeps a tombstone; grants are bound to the credential that asked | |
| Lost revoke / phantom grant | Nothing is published before it is saved. A revoke denies at once in memory even if the save fails, and a failed revoke is reported as `REVOKE_NOT_DURABLE`, never as success | **Double disk fault on approve:** if the directory fsync fails after the rename *and* writing the old state back also fails, an approval reported as failed may still be on disk and take effect after a restart. The error message says so; check the grants list and revoke it |
| Audit loss | An "attempt" line is written before each change and the "committed" line after; committed lines that fail are retried every 30 seconds (at least once) | **No audit hash chain.** Someone with write access to the audit log can edit or delete lines without detection. Accepted inside the LAN envelope |
| Grants file tampering | `grants.json` is mode `0600`, owned by the server user, same trust level as `acl.json` | Not a new boundary: whoever can write it can already write the ACL |
| Notification leaks | The notify hook sends agent name, action, number of paths, request id and a dashboard link. Paths only when `notify_include_paths` is on. The reason is never sent. No approve links, no tokens in URLs. The ntfy token comes from Phoenix at send time and is never logged. Redirects are not followed | Whoever can read the notification topic learns that an agent asked for something, and when |
| Revoke after use | Revoke and expiry are checked on every request | Revoking cannot take back a value already delivered. Rotate the secret if that matters |
| Shared dashboard credential | Unchanged (see above). Approvals are recorded as `dashboard@<ip>` | Anyone with the dashboard password can approve any request |

## Sealed responses

Sealed responses add per-agent transport encryption (NaCl box: X25519 +
XSalsa20-Poly1305) with fresh ephemeral keys per response. This mitigates
network eavesdropping past TLS termination, cross-agent response interception
on shared hosts, MCP tool output leakage, and relabeling attacks.

It does not protect against a compromised agent private key, in-process
memory access after decryption, or server-side compromise.

For the full sealed responses design, wire format, policy controls
(`require_sealed`, `allow_unseal`), and SDK integration, see
[Sealed Responses](sealed-responses.md).

## Out of scope / non-goals

- Internet/WAN exposure, public ingress, or operation on hostile networks
  (see the deployment envelope — this is unsupported, not merely discouraged)
- Host root compromise or kernel compromise
- Hardware side-channel attacks
- Physical extraction from an already-compromised host
- Full enterprise HSM/KMS assurance model
- Per-operator identity on the dashboard (shared credential model)
- DDoS resistance and internet-scale rate limiting

## Recommended operational controls

- Keep the listener on loopback unless other machines need access; the
  moment you bind a non-loopback address, enable the `tls:` block.
- Use mTLS + `deny_bearer` for high-value paths.
- Keep admin ACLs narrow and rotate credentials regularly.
- Enable nonce + short-lived tokens in higher-risk deployments.
- Store data/key/audit files on restricted paths with strict permissions.
- Monitor audit logs for denied access bursts and unusual path access.
- If the dashboard is enabled: use TLS, use a strong password (not PIN),
  monitor for `dashboard.login` denied events in the audit trail, and
  restrict network access to the server to trusted hosts.
- Disable the dashboard when it is not needed.
